# 개인 PM 에이전트 설계 명세

- **문서 상태:** 설계 확정본 — 사용자 최종 검토 대기
- **작성일:** 2026-08-23 (Asia/Seoul)
- **문서 역할:** 제품·UX·에이전트·Planning Core·기술 구현의 최상위 기준 문서
- **제품명:** 아직 확정하지 않음. 본 문서에서는 `Personal PM Agent`로 통칭

---

## 1. 문서 목적

이 문서는 프로젝트, 수업, 과제, 개인 공부, 공모전, 팀 의존성, 고정 일정과 일상 루틴을 한꺼번에 관리하기 어려운 사용자를 위한 **개인 프로젝트 매니저 겸 일정·할 일 운영 에이전트**의 설계를 정의한다.

이 제품은 단순한 투두 앱이나 캘린더가 아니다. 사용자가 모든 작업을 직접 정리하고 우선순위를 판단하는 대신, 에이전트가 비정형 입력을 구조화하고, 현실적인 가용 시간 안에서 실행 순서를 정하고, 일정이 틀어졌을 때 전체 계획을 최소한으로 재조정한다.

이 문서는 다음 질문에 대한 기준 답변을 제공한다.

1. 제품이 해결하려는 핵심 문제는 무엇인가?
2. 사용자는 매일 어떤 방식으로 제품을 사용하는가?
3. 에이전트는 무엇을 자동으로 하고 무엇을 승인받아야 하는가?
4. 프로젝트·마일스톤·작업·의존성·일정은 어떻게 저장되는가?
5. 오늘 할 일과 마감 위험은 어떤 규칙으로 계산되는가?
6. LLM과 결정론적 코드의 책임은 어떻게 나뉘는가?
7. MVP에 반드시 포함되는 기능과 제외되는 기능은 무엇인가?
8. 시스템이 안전하고 테스트 가능하며 설명 가능하려면 어떤 기술 구조가 필요한가?

이 문서는 이후 작성할 구현 계획, 데이터베이스 스키마, API 계약, 테스트 계획, UI 명세의 상위 기준이다.

다음 두 문서는 본 설계에 편입된 **구현 구속력이 있는 상세 규범**이다.

- `2026-08-23-personal-pm-agent-planner-normative-spec.md`: 계획·위험·재계획 알고리즘, 동률 규칙과 참조 테스트 벡터
- `2026-08-23-personal-pm-agent-evaluation-and-pilot-plan.md`: 안전 Hard Gate, 정량 합격선, 4주 파일럿과 출시 판정

문서 우선순위는 다음과 같다.

1. 본 문서의 제품 원칙·권한·범위 결정
2. 위 두 상세 규범의 계산·평가 규칙
3. 구현 계획·API·DB·UI 하위 명세

계획 알고리즘이나 출시 판정처럼 상세 규범이 존재하는 영역에서는 구현자가 임의로 다른 규칙을 선택할 수 없다.

## 2. 문제 정의

### 2.1 사용자의 실제 문제

대상 사용자는 해야 할 일을 모르지 않는다. 문제는 해야 할 일이 여러 프로젝트와 채널에 흩어져 있고, 다음 판단을 계속 직접 내려야 한다는 점이다.

- 지금 무엇을 먼저 해야 하는가?
- 오늘 사용할 수 있는 시간 안에 무엇이 현실적으로 가능한가?
- 과제, 팀 프로젝트, 공모전, 개인 공부가 충돌할 때 무엇을 보호해야 하는가?
- 큰 목표를 어떤 실행 단위로 나눠야 하는가?
- 팀원이 늦어졌을 때 내 일정은 어떻게 달라지는가?
- 계획이 틀어졌을 때 무엇을 미루고 무엇을 줄여야 하는가?
- 작업을 끝냈다고 볼 수 있는 기준은 무엇인가?
- 이번 주 업무량이 실제 가용 시간을 초과하는가?

기존 투두 앱은 사용자가 이미 잘 정리한 작업을 저장한다. 기존 캘린더는 사용자가 이미 결정한 시간을 표시한다. 기존 프로젝트 관리 도구는 사용자가 우선순위와 의존성을 계속 관리해야 한다. 이 제품은 그 사이의 **판단·정리·재조정 노동**을 대신한다.

### 2.2 핵심 제품 명제

> 사용자는 생각나는 정보와 현재 상황을 자연스럽게 입력하고, 에이전트는 이를 구조화하여 현실적인 계획으로 유지·수선한다.

제품의 가치는 할 일을 많이 보여주는 데 있지 않다. 다음 네 가지를 안정적으로 수행하는 데 있다.

1. **정리:** 정리되지 않은 말·문서·이미지에서 프로젝트, 일정, 작업과 마감을 추출한다.
2. **판단:** 마감, 중요도, 의존성, 가용 시간과 컨디션을 바탕으로 우선순위를 정한다.
3. **협상:** 모든 일을 억지로 넣지 않고 연기·축소·중단 후보를 제시한다.
4. **재조정:** 계획이 틀어져도 기존 계획을 최소한으로 변경하면서 위험을 줄인다.

## 3. 목표 사용자와 제품 범위

### 3.1 1차 목표 사용자

MVP의 1차 사용자는 다음 특성을 가진 대학생이다.

- 여러 과목, 과제, 팀 프로젝트와 공모전을 동시에 진행한다.
- 개인 개발 공부나 자격증·영어 공부도 병행한다.
- 프로젝트 관리 경험이 많지 않다.
- 계획을 세우는 것보다 유지하고 다시 조정하는 데 더 큰 부담을 느낀다.
- 문서, 캘린더, 메모, 채팅에 정보가 흩어져 있다.
- PC와 모바일을 모두 사용한다.

초기 제품은 한 명의 사용자가 자신의 생활 전체를 관리하는 **개인 중심 시스템**이다.

### 3.2 팀 프로젝트 범위

MVP는 팀 협업 도구가 아니다. 팀원 계정, 공동 편집, 팀 권한, 댓글과 협업 보드를 제공하지 않는다.

대신 개인 에이전트가 팀 전체 맥락을 이해할 수 있다.

- 회의록과 계획서에서 사용자의 담당 작업을 추출한다.
- 팀원의 작업을 내 작업의 외부 의존성으로 기록한다.
- 팀원 지연이 내 일정에 미치는 영향을 계산한다.
- 회의 전에 확인할 질문이나 공유할 진행 보고 초안을 만든다.
- 팀원의 일정과 업무를 임의로 수정하지 않는다.
- 팀원에게 메시지를 실제 발송하는 행위는 반드시 재확인한다.

### 3.3 확장 방향

MVP 검증 이후 다음 순서로 확장할 수 있다.

1. Gmail·GitHub·Notion 증거 수집
2. 학교 LMS와 과제 공지 연동
3. 다중 사용자와 팀 워크스페이스
4. 네이티브 모바일 앱
5. 고도화된 개인화와 추천
6. 다른 직군을 위한 개인 Chief of Staff 서비스

확장은 가능하지만 MVP 설계가 이 기능들에 의존해서는 안 된다.

## 4. 제품 목표와 비목표

### 4.1 MVP 제품 목표

MVP는 다음 경험을 완성해야 한다.

- 사용자가 자연어나 문서·이미지를 입력하면 에이전트가 작업과 마감을 구조화한다.
- Google Calendar의 고정 일정을 읽어 실제 가용 시간을 계산한다.
- 프로젝트와 과목을 마일스톤과 실행 작업으로 분해한다.
- 오늘의 핵심 결과와 현실적인 작업 큐를 만든다.
- 마감 위험과 주간 과부하를 설명 가능한 방식으로 계산한다.
- 가용 시간, 컨디션, 일정과 진행 상태가 바뀌면 계획을 최소 변경으로 재조정한다.
- 미완료 이유와 실제 작업 시간을 기록해 예상 시간을 보정한다.
- 아침 브리핑, 저녁 체크인, 주간 리뷰를 제공한다.
- 중요한 변경은 제안과 승인 절차를 거친다.
- 외부 행동 성공 여부를 검증하고 실패를 성공처럼 표시하지 않는다.

### 4.2 MVP 비목표

다음은 의도적으로 MVP에서 제외한다.

- 팀원 초대와 공동 프로젝트 편집
- Gmail 전체 자동 감시
- GitHub 커밋·PR 자동 완료 판정
- Notion 양방향 동기화
- 학교 LMS 자동 수집
- 여러 캘린더 제공자 동시 지원
- 네이티브 iOS·Android 앱
- 완전 자동 외부 메시지 발송
- 복잡한 머신러닝 개인화 모델
- 다수의 자율 에이전트가 동시에 상태를 수정하는 구조
- 소셜 기능, 랭킹과 과도한 게임화
- 모든 유연 작업을 캘린더에 강제로 배치하는 기능
- 마이크로서비스와 Kubernetes 기반의 과도한 인프라

## 5. 핵심 설계 원칙

### 5.1 Planning Core가 단일 기준이다

채팅 기록, LLM 메모리, 캘린더, 문서 검색 결과는 공식 상태가 아니다. 프로젝트, 마감, 작업 상태, 예상 시간, 승인과 계획 버전은 Planning Core에 구조화되어 저장되어야 한다.

### 5.2 LLM은 이해하고 설명한다

LLM은 다음을 담당한다.

- 자연어 의도 파악
- 문서와 이미지에서 정보 추출
- 큰 목표의 작업 분해안 생성
- 불확실한 부분 식별
- 계획과 위험의 자연어 설명
- 브리핑과 메시지 초안 생성

LLM은 다음을 직접 결정하거나 실행하지 않는다.

- 데이터베이스 직접 수정
- Hard Deadline 임의 변경
- 권한·승인 정책 우회
- 가용 시간과 마감 위험의 최종 산술 계산
- Google Calendar 직접 호출
- 프로젝트 중단이나 외부 메시지 발송

### 5.3 결정론적 코드는 판단 가능한 규칙을 담당한다

다음은 테스트 가능한 코드로 처리한다.

- 실질 가용 시간 계산
- 작업 실행 가능 여부
- 작업 상태 전이
- 의존성 해소 여부
- 우선순위 등급과 세부 점수
- 마감 위험과 과부하 계산
- 계획 변경 비용
- 승인 필요 여부
- 중복 실행 방지
- 외부 행동 성공 검증

### 5.4 사실·추론·제안·실행을 분리한다

- **사실:** 확인된 마감, 일정, 사용자의 직접 입력
- **추론:** 예상 시간, 위험도, 의존성 추정
- **제안:** 아직 반영되지 않은 변경안
- **실행:** 실제 저장되거나 외부 서비스에 반영된 변경

추론을 사실로 저장하거나 제안을 실행 완료처럼 표시해서는 안 된다.

### 5.5 계획은 완벽함보다 안정성이 중요하다

새 정보가 들어올 때마다 하루 계획 전체를 바꾸지 않는다. 현재 진행 중인 작업과 가까운 시간대의 확정 계획을 보호하고, 위험을 줄이는 데 필요한 최소한의 변경만 수행한다.

### 5.6 과부하를 사용자 노력 부족으로 해석하지 않는다

가용 시간이 20시간인데 업무량이 35시간이면 문제는 의지 부족이 아니라 계획 불가능성이다. 제품은 연기, 축소, 외부 조정과 중단 후보를 제안해야 한다.

### 5.7 모든 자동 변경은 설명·취소 가능해야 한다

자동 변경에는 다음 정보가 필요하다.

- 무엇이 변경되었는가?
- 왜 변경되었는가?
- 어떤 권한 규칙으로 변경되었는가?
- 어떤 계획 버전에서 발생했는가?
- 사용자가 되돌릴 수 있는가?

## 6. 사용자 운영 모델

### 6.1 혼합형 운영 루프

제품은 채팅, 대시보드와 능동 브리핑을 함께 사용한다.

- **채팅:** 새로운 정보 입력, 질문, 명령과 승인
- **대시보드:** 오늘·프로젝트·마감·위험의 전체 현황
- **브리핑:** 사용자가 먼저 앱을 열지 않아도 실행을 유도

### 6.2 초기 온보딩: AI 라이프 오디트

첫 사용은 긴 설정 폼이 아니라 사용자의 현재 업무와 일정 상태를 정리해주는 **AI 라이프 오디트**로 구성한다.

#### 1단계 — 최소 기본 정보

- 시간대
- 평일·주말의 대략적인 활동 가능 시간
- 보호해야 하는 수면·수업·개인 일정
- 이번 학기 또는 현재 기간의 핵심 목표 최대 3개

정확한 생활 패턴을 처음부터 모두 묻지 않는다. 실제 사용 기록으로 점진적으로 학습한다.

#### 2단계 — 기존 자료 가져오기

사용자는 선택적으로 다음을 연결하거나 업로드한다.

- Google Calendar
- 강의계획서
- 프로젝트 계획서
- 기존 투두 목록
- 과제 공지 이미지
- 회의록과 메모

연동이나 파일 없이 자연어 대화만으로도 시작할 수 있어야 한다.

#### 3단계 — 자동 구조 초안

에이전트는 발견한 Area, Workstream, Milestone, Task, Hard Deadline과 외부 의존성을 프로젝트 단위로 묶어서 보여준다. 작업 수십 개를 하나씩 승인시키지 않고 다음처럼 요약한다.

```text
발견된 영역: 4개
프로젝트·과목: 8개
마일스톤: 15개
실행 작업 후보: 31개
향후 30일 Hard Deadline: 9개
출처 충돌: 2개
확인 필요: 5개
```

#### 4단계 — 필요한 내용만 인터뷰

이미 자료에서 확인된 질문은 다시 하지 않는다. 다음과 같은 충돌·우선순위·가용 시간만 확인한다.

- 서로 다른 자료에 적힌 마감 중 어느 날짜가 맞는가?
- 일정이 충돌할 때 반드시 보호해야 하는 목표는 무엇인가?
- 개인 공부는 핵심 유지 목표인가, 여유 시간 목표인가?
- 현실적인 주당 개인 작업 시간은 어느 정도인가?
- 팀 프로젝트에서 사용자의 역할과 기다리는 외부 결과는 무엇인가?

#### 5단계 — 초기 상황 보고서

```text
현재 활성 프로젝트·과목: 8개
주당 안전 예상 작업량: 34시간
주당 실질 가용 시간: 25시간
예상 과부하: 9시간

High Risk
- 데이터베이스 과제: 안전 시간 3시간 부족
- CounterACT: 외부 의존성 전달일 미확인

조정 권장
- 신규 사이드 프로젝트 시작 보류
- 선택적 논문 조사 다음 주 이동
- Spring Boot 추가 실습 범위 축소
```

사용자가 이 초기 기준을 승인하면 첫 주 계획, 오늘 계획과 브리핑 운영을 시작한다.

### 6.3 일일 루프

#### 아침

1. Google Calendar의 오늘 고정 일정을 반영한다.
2. 사용자에게 오늘 가용 시간과 컨디션을 확인한다.
3. 계획 엔진이 오늘 핵심 결과와 작업 큐를 생성한다.
4. 위험 검토기가 마감 누락, 과부하와 무리한 계획을 검사한다.
5. 사용자는 `시작`, `수정`, `오늘은 힘듦` 중 하나를 선택한다.

#### 작업 중

사용자는 다음을 간단하게 기록한다.

- 시작
- 완료
- 부분 완료
- 막힘
- 다른 사람 대기
- 현재 가용 시간 변경
- 새로운 일정·과제 추가

에이전트는 필요한 경우 오늘 후반의 작업 큐만 재계산한다.

#### 저녁

1. 완료·부분 완료·미완료 상태를 확인한다.
2. 미완료 이유를 짧게 분류한다.
3. 실제 작업 시간을 기록한다.
4. 남은 작업량을 다시 추정한다.
5. 자동 이동 가능한 작업과 승인 필요한 변경을 분리한다.
6. 내일 계획에 미치는 영향을 보여준다.

### 6.4 주간 루프

주간 리뷰는 통계 구경이 아니라 다음 주 계획을 승인하는 과정이다.

- 이번 주 주요 결과물
- 계획 대비 실제 시간
- 프로젝트별 진척과 병목
- 반복되는 미완료 원인
- 향후 14일 마감 위험
- 다음 주 가용 시간과 안전 예상 작업량
- 연기·범위 축소·중단 후보
- 다음 주 핵심 결과 최대 3개

## 8. 정보 구조

### 8.1 계층 구조

```text
Workspace
└─ Area
   └─ Workstream
      └─ Milestone
         └─ Task
```

사용자 화면에서는 Workstream의 종류에 따라 과목, 프로젝트, 공모전, 공부 목표 등으로 표시한다.

### 8.2 보조 객체

- Routine
- External Dependency
- Calendar Event
- Availability
- Inbox Item
- Source Artifact
- Work Session
- Completion Evidence
- Plan Snapshot
- Proposal
- Approval
- Audit Event
- Estimation Profile

### 8.3 Area

장기간 유지되는 생활 분야이다.

예시:

- 학교
- 팀 프로젝트
- 공모전
- 개인 개발
- 영어 공부
- 건강

주요 필드:

- 이름과 설명
- 상태
- 기본 중요도
- 주간 시간 예산
- 표시 순서

### 8.4 Workstream

프로젝트, 과목, 공부 목표와 건강 프로그램을 포괄한다.

주요 필드:

- 이름과 종류
- 소속 Area
- 목표와 성공 조건
- 시작일과 목표 종료일
- 상태
- 중요도
- 사용자 역할
- 주당 권장·최대 시간
- 자동화 허용 수준

중요도는 사용자가 다음 등급 중 하나로 설정한다.

- 반드시 보호
- 중요
- 일반
- 선택
- 보류

에이전트는 이를 임의로 변경하지 않고 조정 필요성을 제안한다.

### 8.5 Milestone

마일스톤은 확인 가능한 결과물이어야 한다.

예시:

- 데이터베이스 과제 2 제출
- CounterACT 1차 프로토타입 시연
- 공모전 기획서 제출
- 중간고사 응시

마감 유형:

1. **Hard Deadline:** 넘기면 실제 손해가 발생하는 제출·시험
2. **External Commitment:** 팀·교수·외부인과 약속한 일정
3. **Internal Target:** 실제 마감 전에 확보한 내부 목표
4. **Soft Goal:** 이동 가능한 권장 목표일

### 8.6 Task

Task는 사용자가 지금 실제로 시작할 수 있는 행동 단위다. 기본 크기는 30분에서 2시간으로 유지하되 자연스러운 작업 단위를 우선한다.

주요 필드:

- 제목과 설명
- 소속 Workstream과 Milestone
- 상태
- 마감일과 마감 유형
- 시작 가능 시점
- 기준 예상 시간 `base_duration_minutes`
- 안전 예상 시간 `safety_duration_minutes`
- 남은 예상 시간
- 불확실성
- 최소 실행 단위
- 분할 가능 여부
- 필요 집중도와 에너지
- 필요 장소와 도구
- 선행 작업
- 완료 조건
- 완료 증거 정책
- 외부 담당자
- 출처
- 자동 변경 허용 범위
- 객체 버전

Task 상태:

- Draft
- Planned
- Ready
- In Progress
- Waiting
- Blocked
- Done
- Deferred
- Cancelled

### 8.7 Routine

반복 행동은 템플릿과 날짜별 발생 항목을 분리한다.

예시:

- TOEIC 단어 복습
- 주간 회고
- 운동

루틴에는 기본 수행량과 최소 수행량을 둔다. 과부하 시 전체 삭제보다 최소 수행량으로 축소할 수 있다.

### 8.8 External Dependency

팀원이나 외부 서비스가 제공해야 하는 결과를 나타낸다.

예시:

```text
항목: 팀원의 데이터셋 정리
담당자: 민수
예상 전달일: 수요일
영향받는 내 작업: 모델 평가
상태: 대기 중
```

외부 의존성을 팀원의 Task처럼 직접 통제하지 않는다.


### 8.9 Task Dependency

Task 간 관계는 다음 유형을 지원한다.

- **Blocks Start:** 앞 작업이 끝나야 후행 작업을 시작할 수 있음
- **Blocks Completion:** 후행 작업을 시작할 수 있지만 앞 작업 없이는 완료할 수 없음
- **Waiting For External:** 다른 사람·승인·외부 시스템 결과를 기다림
- **Related:** 직접 막지는 않지만 계획과 설명에서 함께 고려

의존성 그래프는 단순 마감 순서보다 다른 작업을 많이 해제하는 병목 Task를 먼저 찾는 데 사용한다.

### 8.10 프로젝트 진행률

작업 개수로 진행률을 계산하지 않는다. 승인된 범위의 예상 노력량을 기준으로 한다.

```text
실행 진행률 =
완료된 Task의 승인 예상 노력량
/
전체 승인 범위의 예상 노력량
```

사용자 화면에는 다음을 함께 보여준다.

- 실행 진행률
- 마감 가능성
- 현재 병목
- 외부 의존성

10분짜리 작업 여러 개를 끝냈다고 핵심 구현이 남은 프로젝트를 거의 완료된 것으로 표시해서는 안 된다.

## 11. 가용 시간 모델

### 11.1 Google Calendar의 역할

Google Calendar는 다음을 관리한다.

- 수업
- 회의
- 시험
- 약속
- 제출 시각
- 확정된 집중 블록

Planning Core는 다음을 관리한다.

- 프로젝트
- 마일스톤
- 작업과 작업 큐
- 우선순위
- 예상 시간
- 의존성
- 완료 조건

유연한 Task를 전부 캘린더 이벤트로 만들지 않는다. 사용자가 실행 시점을 확정한 집중 블록만 캘린더에 생성한다.

### 11.2 일정 유형

- Fixed Busy
- Movable Commitment
- Tentative
- All-day Information

All-day 정보는 실제 하루 전체를 자동으로 차단하지 않는다.

### 11.3 실질 가용 시간

```text
실질 가용 시간 =
min(캘린더 기반 가용 시간, 사용자 선언 가용 시간)
- 이동 시간
- 식사·휴식
- 작업 전환 시간
- 보호 버퍼
```

가용 시간을 100% 채우지 않는다.

초기 기준:

- 일반적인 날: 75~80%
- 컨디션 낮음: 60~70%
- 마감 집중 기간: 최대 85%

실제 기록이 쌓이면 개인별로 보정한다.

## 12. 계획 엔진 규범

계획 엔진의 상세 계산 규칙은 `2026-08-23-personal-pm-agent-planner-normative-spec.md`를 따른다. 이 절은 구현에서 변경할 수 없는 핵심 규칙을 요약한다.

### 12.1 결정론성과 입력 계약

Planner는 현재 시각을 내부에서 읽지 않고 다음을 명시적으로 입력받는다.

- `planner_version`
- `now_utc`와 사용자 시간대
- 계획 기간
- 가용 시간과 캘린더 일정
- Task·Milestone·의존성·외부 의존성
- 사용자별 예상 시간 보정값
- 기존 Plan Snapshot
- 자동화 권한과 사용자 고정 항목

입력을 Canonical 형태로 정규화하여 `input_hash`를 생성한다. 동일한 입력과 Planner 버전은 동일한 Task 순서, 슬롯 배정, 위험 등급과 변경안을 생성해야 한다. 난수와 LLM 점수는 핵심 정렬에 사용할 수 없다.

### 12.2 시간 추정 용어

초기 제품은 충분히 교정된 통계 분포가 없으므로 Task 시간을 P50·P90이라고 부르지 않는다.

- `base_duration_minutes`: 현재 정보에서 가장 가능성이 높은 기준 예상 시간
- `safety_duration_minutes`: 마감 안전성 계산에 사용하는 보수적 예상 시간

개별 Task의 안전 예상 시간을 합한 값은 프로젝트 전체의 통계적 P90이라고 표현하지 않는다. `총 기준 수요`와 `총 안전 수요`로 표시한다.

### 12.3 시간과 날짜

- 저장 시각은 UTC, 표시와 해석은 사용자 시간대를 사용한다.
- 상대 날짜는 입력 시각과 사용자 시간대를 기준으로 절대 날짜로 변환하고 원본 표현을 보존한다.
- 마감 날짜만 있고 시각이 없으면 `time_known=false`로 저장한다.
- 날짜만 있는 마감에 임의로 23:59를 사실처럼 저장하지 않는다.
- 계산상 보수 경계는 해당 날짜 00:00을 사용하고, 사용자 확인 전까지 위험은 Low가 될 수 없다.
- 요일과 날짜가 충돌하면 자동 등록하지 않는다.

### 12.4 의존성 그래프 검증

`Blocks Start` 실행 그래프와 `Blocks Start + Blocks Completion` 완료 가능성 그래프를 별도로 만들고 계산 전에 사이클을 탐지한다. `Blocks Completion`은 작업 시작을 막지 않고 Done 상태 전이만 막는다. 실제 후속 작업 시간이 필요하면 별도 Task와 `Blocks Start`로 표현한다.

사이클이 있으면:

- 관련 Task를 계획에 배정하지 않는다.
- `Blocked: Dependency Cycle` 후보로 표시한다.
- 관련 작업량은 마감 위험에서 제거하지 않는다.
- 정확한 사이클 경로를 사용자에게 보여준다.
- 에이전트가 임의로 연결을 삭제하거나 방향을 바꾸지 않는다.

### 12.5 고유 시간 슬롯

시간 슬롯 기본 단위는 15분이다. 한 Planner Pass 안에서 하나의 슬롯은 정확히 하나의 일정·Task·버퍼에만 속할 수 있다.

```text
FREE
FIXED_EVENT
PROTECTED_FOCUS_BLOCK
TASK_ALLOCATION
BUFFER
```

같은 가용 시간을 여러 Task의 Coverage 계산에 중복 사용할 수 없다.

### 12.6 Base Pass와 Safety Pass

Planner는 동일한 공유 용량을 대상으로 두 번의 독립된 전역 배정을 수행한다.

```text
Base Pass
- base_duration_minutes 사용
- 실제 실행 가능한 최소 계획 검증

Safety Pass
- safety_duration_minutes 사용
- 검토·테스트·제출 버퍼 포함
- 안전 마감 가능성 검증
```

검토·테스트·제출 버퍼는 단순 가산값이 아니라 P1 Synthetic Task로 만들어 다른 작업과 같은 슬롯을 사용하게 한다.

### 12.7 전역 용량 배정 순서

각 Pass는 다음 순서로 실행한다.

1. 입력·권한·시간 범위 검증
2. 의존성 사이클 탐지
3. 고정 일정·수면·이동·휴식 제거
4. 일일 계획 가능 비율 적용
5. 기존 보호 계획 예약
6. 초기 P0~P4 등급으로 Provisional Base Pass 실행
7. 기준 시간이 미배정된 필수 경로를 P0로 한 번 승격
8. 최종 등급으로 Base Pass와 Safety Pass 실행
9. 실행 가능한 후보 집합 생성
10. 안정적인 우선순위 키로 Task 선택
11. 분할 가능 여부와 최소 연속 블록 확인
12. 가능한 가장 이른 고유 슬롯에 배정
13. 후행 Task 해제
14. 미배정 기준·안전 작업량 계산

Base Pass와 Safety Pass는 각각 가용 슬롯을 처음부터 새로 복제해 실행한다. 한 Pass 내부에서는 슬롯 중복이 0건이어야 한다.

### 12.8 우선순위와 결정론적 동률 처리

초기 등급으로 Provisional Base Pass를 한 번 실행하고, 기준 시간이 미배정된 필수 경로를 P0로 승격한 뒤 최종 Base·Safety Pass를 실행한다. 등급은 다음 순서를 따른다.

1. **P0 Rescue:** Provisional Base Pass 불가능, 마감 초과, 회복 불가능한 핵심 외부 지연
2. **P1 Protect:** 제출·시험·외부 약속·병목·필수 버퍼
3. **P2 Progress:** 중요 프로젝트와 주간 핵심 결과를 전진시키는 작업
4. **P3 Maintain:** 운동·복습·주간 회고 등 지속성 유지
5. **P4 Optional:** 추가 조사·부가 기능·디자인 개선

같은 등급 안에서는 다음 Tuple을 순서대로 비교한다.

```text
priority class
→ must-start-by
→ effective deadline
→ critical-path unlock count
→ external commitment
→ user importance
→ prior plan position
→ context-switch penalty
→ created_at
→ task_id
```

가중합 점수는 설명용으로만 사용할 수 있으며 실제 정렬을 대체하지 않는다.

### 12.9 오늘 계획

오늘 계획은 Base Pass의 오늘 배정을 기준으로 하되 Safety Pass가 확보한 안전 버퍼를 침범하지 않는다.

```text
오늘의 핵심 결과 1개
반드시 완료할 작업 1~3개
그다음 작업 큐
남는 시간에 할 작업
오늘 하지 않을 작업
현재 위험과 필요한 결정
```

필수 규칙:

- 계획 시간이 일일 계획 가능 용량을 초과하지 않는다.
- P0·P1 미배정 수요가 있으면 P4를 넣지 않는다.
- `반드시 완료`에는 오늘 필요한 기준 시간이 전부 배정된 Task만 넣는다.
- In Progress Task는 첫 번째에 유지한다.
- 고집중 Workstream은 기본 최대 2개다.
- Routine은 P0·P1을 밀어내지 않는다.

### 12.10 최소 변경 재계획

재계획은 다음 목표를 사전식으로 최소화한다.

```text
1. Hard Constraint 위반
2. 권한·승인 위반
3. Critical 마일스톤 수
4. Base Pass 미배정 시간
5. High 마일스톤 수
6. Safety Pass 미배정 시간
7. 기존 계획 변경 비용
8. 프로젝트 전환 수
9. 에너지·시간대 부적합
```

앞 항목의 악화를 뒤 항목의 이득으로 상쇄할 수 없다.

보호 규칙:

- In Progress·Fixed Event·사용자 Pin: 자동 이동 금지
- 앞으로 120분 이내 확정 계획: 자동 이동 금지
- Critical 해소에 보호 구간 변경이 필요하면 Proposal과 사용자 승인이 필요

### 12.11 Planner 출력

모든 결과에는 다음을 포함한다.

- `planner_version`
- `input_hash`
- Base Plan과 Safety Plan
- Today Plan
- 마일스톤·외부 의존성 위험
- 미배정 기준·안전 시간
- Proposal
- 기존 계획과 차이
- Rule ID 기반 판단 근거
- 검증 경고와 미해결 항목

자연어 설명은 이 구조화된 근거만 사용한다.

### 12.12 필수 참조 테스트

상세 규범 문서의 참조 벡터를 100% 통과해야 한다.

- 두 마감이 같은 4시간 용량을 공유하는 충돌
- 완전 동률 Task의 안정적 순서
- 의존성 사이클
- 시각 미확인 날짜 마감
- 여유가 있는 외부 의존성
- 안전 인계 시각을 넘긴 외부 의존성
- 120분 동결 구간
- 연속 시간이 필요한 비분할 Task
- Base 가능·Safety 불가능
- 한 Task만 옮기면 되는 최소 변경 재계획

## 13. 마감 위험과 과부하 규범

### 13.1 전역 배정 기반 Coverage

Coverage는 각 작업을 독립적으로 계산하지 않고 전역 Base·Safety Pass가 실제로 배정한 고유 슬롯에서 계산한다.

```text
base_coverage =
Base Pass에서 유효 마감 전 배정된 필수 시간
/
총 기준 수요

safety_coverage =
Safety Pass에서 유효 마감 전 배정된 필수 시간
/
총 안전 수요
```

하나의 슬롯이 둘 이상의 작업 Coverage에 사용되면 구현 오류다.

### 13.2 Slack

```text
미배정 필수 시간이 있으면:
slack = -미배정 시간

모든 필수 시간이 배정됐으면:
slack = Safety Pass 후 실제 사용 가능한 잔여 고유 슬롯
```

잔여 슬롯은 해당 마일스톤 Task가 장소·도구·시간 조건상 실제 사용할 수 있는 슬롯만 센다.

### 13.3 위험 판정 순서

#### Definitive Critical

- 시각까지 확인된 마감이 지났고 필수 결과가 미완료
- 날짜만 확인된 마감의 다음 로컬 날짜가 되었는데 필수 결과가 미완료
- 핵심 외부 의존성이 최종 안전 인계 시각을 지났고 대체 경로 없음
- 의존성 사이클로 필수 경로 시작 불가

#### Unknown

- 마감·필수 범위·기준 시간 중 하나가 없음
- 마감 날짜만 있고 시각이 미확인
- 필수 외부 의존성의 전달 예상이 없음

날짜만 있는 당일 마감은 계산상 00:00을 사용하더라도 Base Pass 미배정을 이유로 Critical로 올리지 않는다.

#### Capacity Critical

핵심 정보가 모두 확인된 상태에서 Base Pass Coverage < 1.0이면 Critical이다.

#### High

- Base Pass는 가능하지만 Safety Pass Coverage < 1.0
- 필수 검토·테스트·제출 버퍼 일부 미배정
- 외부 결과 예상 전달이 최종 안전 인계 시각보다 늦음

#### Medium

Safety Pass는 가능하지만 다음 중 하나다.

```text
slack < max(30분, 총 안전 수요의 10%)
```

또는 외부 전달 여유가 불확실성 버퍼 이하이다.

#### Low

- Base·Safety Coverage 모두 1.0
- 필수 버퍼 전부 배정
- Medium 기준보다 큰 양의 Slack
- 핵심 정보 모두 확인

### 13.4 외부 의존성

외부 결과의 미완료 여부만으로 Critical을 부여하지 않는다.

```text
latest_safe_handoff_at =
후행 작업의 안전 시간과 필수 버퍼를 역산했을 때
외부 결과가 도착할 수 있는 최종 시각
```

- 현재 시각이 최종 안전 인계 시각을 지났고 대체 경로 없음: Critical
- 예상 전달이 최종 안전 인계보다 늦음: High
- 전달 여유가 불확실성 버퍼 이하: Medium
- 충분한 전달 여유: Low
- 전달 예상 또는 후행 시간 정보 없음: Unknown

### 13.5 과부하 종류

- Daily Overload
- Deadline Overload
- Weekly Overload
- Context Overload
- Cognitive Overload
- Commitment Overload

모든 주요 마감 Prefix를 같은 전역 배정 결과에서 누적 검사한다.

### 13.6 과부하 협상 순서

1. P4 선택 작업 제거
2. 이동 가능한 P3·낮은 P2 연기
3. 작업 범위 축소 제안
4. 역할·일정·요구사항 외부 조정 제안
5. 사용자 최대치 안의 제한적 추가 시간 제안
6. 프로젝트 중단·포기 검토

각 Proposal에는 변경 전후, 확보·절감 시간, 영향받는 마일스톤, 변경 후 Base·Safety Coverage, 위험 등급, 승인 수준과 되돌리기 가능 여부를 포함한다.

수면·수업·회복 시간을 무시하거나 권한 규칙을 우회하는 조정안은 생성하지 않는다.

## 14. 진행과 완료 추적

### 14.1 Work Session

계획 시간과 실제 작업 시간을 분리한다.

```text
계획 시간
실제 시작·종료
실제 집중 시간
결과: 완료 / 부분 완료 / 중단
중단 이유
남은 예상 시간
```

### 14.2 완료 방식

- 단순 작업: 사용자 자연어·버튼 완료
- 연동 가능한 작업: 활동 증거 기반 완료 제안
- 중요한 산출물: 완료 조건 검사 후 사용자 확인

MVP에서는 사용자 직접 확인과 파일·세션 증거를 중심으로 한다. GitHub·Gmail 기반 자동 증거는 후속 버전이다.

### 14.3 부분 완료

완료한 부분과 남은 범위를 분리하고 남은 예상 시간을 다시 계산한다. 전체 작업을 무조건 처음부터 재계획하지 않는다.

### 14.4 Blocked와 Waiting

- **Blocked:** 사용자가 해결해야 하는 문제
- **Waiting:** 다른 사람·승인·자료·외부 서비스 대기

두 상태를 구분하여 병목 원인을 분석한다.

### 14.5 예상 시간 학습

초기에는 간단한 통계적 보정을 사용한다.

- 1~2건: 참고만 함
- 3~5건: 약한 보정
- 6건 이상: 기본 추정에 반영

관찰 데이터로만 설명한다. 사용자의 성격을 평가하지 않는다.

## 15. 에이전트 구성

### 15.1 Agent Orchestrator

요청을 분류하고 전문 모듈의 실행 순서, 권한과 결과 검증을 관리한다.

### 15.2 Intake & Structuring Worker

비정형 입력을 프로젝트·마감·작업·일정 후보로 변환하고 불확실성을 표시한다.

### 15.3 Project Decomposition Worker

큰 목표를 실행 가능한 작업으로 분해하고 예상 시간, 의존성과 완료 조건을 제안한다.

### 15.4 Deterministic Planning Engine

실행 가능성, 우선순위, 마감 위험, 과부하와 오늘 계획을 계산한다.

### 15.5 Risk Reviewer

계획을 새로 만들지 않고 다음을 검증한다.

- 검토·제출 버퍼 누락
- 선행 관계 오류
- 고정 일정 충돌
- 가용 시간 초과
- 장기 프로젝트 방치
- 승인되지 않은 범위 변경
- 외부 의존성 무시

MVP에서는 규칙 기반 검사를 중심으로 하고 LLM은 설명에만 사용한다.

### 15.6 Action Executor

승인된 내부 명령과 외부 행동을 실행하고 실제 성공 여부를 검증한다.

### 15.7 Progress & Analytics Service

실제 시간, 미완료 원인, 재계획 횟수와 사용자별 보정값을 관리한다.

### 15.8 Briefing Generator

Planning Core의 결과를 아침·저녁·주간에 필요한 정보로 압축한다.

### 15.9 공통 실행 루프

```text
Observe
→ Interpret
→ Retrieve
→ Plan
→ Critique
→ Authorize
→ Act
→ Verify
→ Explain
→ Learn
```

- 승인 필요 제안
- 시작·완료·부분 완료·막힘·재계획 행동

### 16.2 인박스

- 원본 입력
- 에이전트 해석
- 신뢰도
- 확인이 필요한 필드
- 확정·수정·메모·병합·무시

### 16.3 프로젝트

- 현재 마일스톤
- 실행 진행률
- 마감 가능성
- 다음 핵심 작업
- 병목과 외부 대기
- 마일스톤 타임라인
- Ready·Waiting·Blocked·Done 상태 요약

진행률과 마감 가능성을 분리하여 표시한다.

### 16.4 캘린더

- 고정 일정
- 제출 마감
- 승인된 집중 블록
- 임시 일정

- 아직 배치되지 않은 작업 큐
- 내부 저장과 외부 반영 상태

### 16.5 리뷰

- 이번 주 주요 결과물
- 계획 대비 실제 시간
- 프로젝트별 상태

### 16.7 PC와 모바일의 역할

PC에서는 전체 상황을 검토하고 구조를 수정한다.

- 주간 리뷰
- 위험과 과부하 비교
- 계획 승인과 직접 수정

- 갑자기 생긴 작업 입력
- 아침 브리핑 확인
- 작업 시작·완료·부분 완료
- 컨디션과 가용 시간 변경
- 승인 카드 응답
- 저녁 체크인

초기에는 네이티브 앱이 아니라 반응형 Web/PWA와 Web Push를 사용한다.

## 17. 알림과 브리핑 정책

### 17.1 알림 등급

- **Critical:** 즉시 행동하지 않으면 실제 손해 가능성이 큼
- **Actionable:** 사용자의 현재 결정이 필요함
- **Summary:** 아침·저녁·주간 묶음 전달
- **Silent:** 기록만 하고 즉시 알리지 않음

### 17.2 기본 빈도

일반적인 날에는 다음 수준을 목표로 한다.

- 아침 브리핑 1회
- 행동 필요 알림 0~2회
- 저녁 체크인 1회
- Critical은 예외

같은 위험을 반복 알리지 않고 발송 직전에 문제가 아직 유효한지 다시 확인한다.

### 17.3 표현 원칙

사용자를 평가하거나 압박하지 않는다.

피해야 할 표현:

- 생산성이 낮습니다.
- 오늘도 실패했습니다.
- 계획을 지키지 않았습니다.

권장 표현:

- 계획보다 집중 시간이 50분 적었습니다.
- 남은 작업은 약 70분입니다.
- 내일 이동 또는 범위 축소가 가능합니다.

## 18. 기술 아키텍처

### 18.1 선택한 구조

```text
Next.js 반응형 Web/PWA
          ↓ REST / SSE
FastAPI Modular Monolith
          ↓
PostgreSQL · Redis · Object Storage
          ↓
Background Worker · Google Calendar · LLM Provider · Notification
```

### 18.2 선택 이유

- Next.js는 PC·모바일 반응형 UI와 PWA에 적합하다.
- FastAPI는 Python 기반 Planning Core와 AI 서비스를 일관되게 구현할 수 있다.
- 모듈형 모놀리스는 초기 배포를 단순하게 유지하면서 도메인 경계를 보존한다.
- PostgreSQL은 마감·의존성·승인·트랜잭션을 안정적으로 관리한다.
- Redis는 작업 큐, 짧은 캐시와 분산 잠금에 사용한다.
- Object Storage는 원본 문서와 이미지를 보존한다.

### 18.3 백엔드 모듈

- identity
- inbox
- workspaces
- planning
- agent
- approvals
- calendar
- execution
- notifications
- analytics
- audit
- shared

한 모듈이 다른 모듈 테이블을 직접 수정하지 않는다. 애플리케이션 명령과 서비스 인터페이스를 통한다.

### 18.4 계층 구조

- API Layer
- Application Layer
- Domain Layer
- AI Layer
- Infrastructure Layer

Domain Layer는 프레임워크, 데이터베이스, 네트워크와 LLM 없이 테스트할 수 있어야 한다.

### 18.5 통신

- 일반 CRUD와 계획·승인: REST
- 채팅 응답과 문서 처리 진행: SSE
- 실시간 공동 편집이 없으므로 MVP에서 WebSocket은 필수 아님

### 18.6 OpenAPI 계약

FastAPI의 Pydantic Schema에서 OpenAPI를 생성하고 TypeScript API 클라이언트와 타입을 자동 생성한다.


### 18.7 권장 모노레포 구조

```text
project-root/
├─ apps/
│  ├─ web/
│  └─ api/
├─ packages/
│  ├─ api-client/
│  ├─ ui/
│  └─ config/
├─ infra/
├─ docs/
└─ scripts/
```

FastAPI 내부는 도메인 모듈별로 나누고 Planning Engine은 네트워크·DB·LLM과 분리된 순수 Python 패키지처럼 유지한다.

### 18.8 배포 단위

MVP의 런타임은 다음으로 제한한다.

- Web
- API
- Worker
- PostgreSQL
- Redis
- Object Storage
- Monitoring

로컬 개발은 Docker Compose로 재현한다. 환경은 local, test, staging, production으로 나눈다. Kubernetes와 서비스 메시는 사용하지 않는다.

## 19. 데이터 저장과 변경 안전성

### 19.1 PostgreSQL

다음은 정규 필드로 관리한다.

- 상태
- 마감일
- 프로젝트 ID
- 예상 시간
- 우선순위
- 승인 상태
- 객체 버전
- 외부 이벤트 ID

LLM의 부가 추론과 임시 메타데이터만 제한적으로 JSON 필드에 저장한다.

### 19.2 문서 검색

벡터 검색은 회의록, 참고자료와 과거 문서 검색에만 사용한다. 정확한 마감, 작업 상태, 승인과 가용 시간의 기준 저장소로 사용하지 않는다.

### 19.3 동시 수정

낙관적 잠금을 사용한다.

```text
요청 객체 버전 != 현재 객체 버전
→ 자동 덮어쓰기 금지
→ 최신 상태 재조회
→ 영향 재계산
```

### 19.4 계획 버전

모든 계획은 Plan Snapshot으로 저장한다.

- 생성 시각
- 입력 상태 버전
- 핵심 결과
- 계획 항목
- 위험 상태
- 이전 계획과 변경점
- 변경 원인
- 자동 또는 승인 여부

### 19.5 Audit Event

중요 변경은 다음을 기록한다.

- 주체
- 변경 전후
- 이유
- 권한 근거
- 관련 계획 버전
- 실행 결과
- 되돌리기 가능 여부

- 브리핑 생성

### 21.2 작업 상태

- Queued
- Running
- Succeeded
- Failed
- Retrying
- Cancelled
- Dead Letter

### 21.3 멱등성

모든 외부 행동과 비동기 작업에 Idempotency Key를 사용한다. 재시도로 같은 캘린더 이벤트나 작업이 중복 생성되어서는 안 된다.

### 21.4 Outbox 패턴

```text
→ 사용자에게 동기화 상태 표시
```

내부 저장과 외부 반영 상태를 명확히 분리한다.

MVP 운영 복잡성을 줄이기 위해 주 모델과 보조 모델 정도로 시작한다.

- entities
- candidate_tasks
- candidate_events
- dependencies
- uncertainties
- confidence
- source_references
- requested_actions

서버 검증을 통과하지 못하면 Planning Core를 변경하지 않는다.

### 22.4 컨텍스트 구성

사용자의 전체 대화와 모든 문서를 매번 모델에 넣지 않는다. 요청과 관련된 검증된 사실, 최근 상태와 필요한 문서만 선택한다.

모델 입력에서 다음을 구분한다.

- SYSTEM POLICY
- VERIFIED FACTS
- USER REQUEST
- UNTRUSTED SOURCE CONTENT
- OUTPUT SCHEMA

## 23. Google Calendar 연동

### 23.1 동기화 방향

Google Calendar → Agent:

- 고정 일정
- 회의·수업·시험
- 사용자가 캘린더에서 변경한 집중 블록

Agent → Google Calendar:

- 승인된 집중 블록
- 사용자가 확정한 일정
- 승인된 집중 블록 이동

### 23.2 연결 필드

- internal_event_id
- provider
- external_calendar_id
- external_event_id
- external version
- last_synced_at
- sync_status

### 23.3 충돌

사용자가 외부 캘린더에서 집중 블록을 이동하면 원래 시간으로 강제 복원하지 않는다. 내부 상태 반영 후보를 만들고 위험 변화를 계산한다.

고정 일정과 집중 블록이 충돌하면 고정 일정을 보호한다.

### 23.4 실패 표시

```text
내부 계획 저장 완료
Google Calendar 반영 실패
원인: 권한 만료
```

외부 반영 실패를 성공으로 표현하지 않는다.

## 25. 보안과 개인정보

### 25.1 최소 권한

Google Calendar 등 외부 서비스는 기능에 필요한 최소 권한만 요청한다. 읽기와 쓰기 권한을 단계적으로 분리한다.

- 원본 파일 삭제

## 26. 테스트 전략

### 26.1 도메인 단위 테스트

- 가용 시간 계산
- 작업 실행 가능 여부
- 상태 전이
- 의존성 처리

- 과부하 조정 순서

### 26.2 불변 조건 테스트

- 완료 Task가 실행 큐에 들어가지 않음
- Waiting·Blocked Task가 Ready로 계획되지 않음
- 선행 작업보다 후행 작업이 먼저 계획되지 않음
- Hard Deadline이 자동 변경되지 않음
- 계획 시간이 실질 가용 시간을 초과하지 않음
- 버퍼가 이유 없이 제거되지 않음
- 같은 입력은 같은 결과를 생성함
- 실패한 외부 행동이 성공으로 기록되지 않음
- 같은 외부 행동이 중복 실행되지 않음

### 26.3 시나리오 테스트

1. 정상적인 한 주
2. 내일까지 5시간 부족한 과제

### 26.4 LLM 계약 테스트

- 출력 스키마 준수

### 26.5 골든 데이터셋

## 27. 품질 게이트와 파일럿 판정

상세 Metric ID, 데이터셋 구성, 사고 등급과 계산식은 `2026-08-23-personal-pm-agent-evaluation-and-pilot-plan.md`를 따른다. 지표를 측정만 하고 합격선을 정하지 않는 방식은 허용하지 않는다.

### 27.1 평가 단계

```text
Stage A — 정적·도메인 검증
Stage B — 골든 데이터셋·LLM 오프라인 평가
Stage C — 외부 연동·장애 복구 검증
Stage D — 실제 사용자 4주 파일럿
```

앞 단계의 Hard Gate를 통과하지 못하면 다음 단계로 진행하지 않는다.

### 27.2 안전·권한 Hard Gate

다음은 전부 0건이어야 한다.

- 승인 없는 Hard Deadline 변경
- 승인 없는 Fixed Event 변경·삭제
- 사용자 데이터 소유권 우회
- 실패한 외부 행동을 성공으로 표시
- 같은 외부 행동 중복 실행
- 문서 지시문이 실제 도구 행동으로 실행
- 슬롯 중복 배정
- 의존성 순서 위반
- Fixed Busy와 Task 중첩
- 확정 계획의 가용 용량 초과
- 날짜만 있는 마감에 임의 시각을 사실 저장
- 실패한 재계획이 마지막 정상 계획을 덮어쓰기

이 항목은 평균이나 비율로 완화할 수 없다.

### 27.3 계획 엔진 합격선

- 규범 참조 테스트 벡터: 100% 통과
- 속성 기반 생성 시나리오: 최소 20,000개, 불변 조건 위반 0건
- 동일 입력 반복 실행 일치율: 100%
- P0·P1 Task Recall: 98% 이상
- 전문가 위험 등급 Macro F1: 0.90 이상
- 승인 유형 정확도: 100%
- 비Critical 재계획의 Median 변경 비율: 20% 이하
- 위험 감소 없이 계획을 변경한 비율: 2% 이하

참조 성능 조건:

```text
Task 500개
계획 기간 42일
15분 슬롯
의존성 1,000개 이하
```

- Base + Safety Pass P95: 3초 이하
- 오늘 재계획 P95: 1.5초 이하
- Peak Memory: 1GB 이하

### 27.4 LLM 입력 구조화 합격선

- First-pass 스키마 성공률: 98.5% 이상
- 1회 복구 후 최종 스키마 성공률: 99.5% 이상
- 자동 등록된 마감·일정의 원본 출처 연결률: 100%
- 원본에 없는 마감 시각 생성: 0건
- Hard Deadline 날짜·시각 Precision: 99% 이상
- Hard Deadline 날짜·시각 Recall: 95% 이상
- 자동 등록 대상 Precision: 99.5% 이상
- 고위험 모호성 확인 전환 Recall: 98% 이상
- 전체 자동 등록 오류율: 0.5% 이하
- Hard Deadline·고정 일정 자동 등록 오류율: 0.2% 이하
- 출처 충돌 자동 선택: 0건

LLM의 자기 보고 confidence를 단독 자동화 기준으로 사용하지 않는다. `model_confidence`, `evidence_score`, `calibrated_probability`, `expected_harm`을 분리한다.

### 27.5 외부 실행 합격선

- 정상 권한 상태 Calendar 쓰기 성공률: 99.5% 이상
- 동일 Idempotency Key 중복 이벤트: 0건
- 내부 성공·외부 실패 상태 혼동: 0건
- 권한 만료 감지 정확도: 100%
- Outbox 유실: 0건
- 외부 반영 완료 P95: 60초 이하
- Webhook 누락 후 주기 동기화 복구: 15분 이내

Timeout, 429, 5xx, OAuth 만료, Worker 중복 실행과 프로세스 중단을 주입한 테스트에서도 중복 생성과 거짓 성공은 0건이어야 한다.

```text
회의록·팀 계획서       40개
```

최소 정답 수:

- 출처 충돌 50개

#### Dogfood

- Week 4 활성 잔존율: 60% 이상
- 자동화 신뢰 중앙값: 5.5/7 이상
- 주간 가치 평가 중앙값: 5.5/7 이상
- 과부하 Proposal 승인 또는 수정 승인율: 60% 이상
- 사용자가 `판단이 틀림`을 이유로 Proposal을 거절한 비율: 15% 이하
- 일반적인 날 알림 중앙값: 4회 이하

- 시스템 오판이 직접 원인이 된 Hard Deadline 지연: 0건

Week 4 활성 사용자는 단순 로그인이 아니라 다음을 모두 만족해야 한다.

- 주 3일 이상 사용

실제 행동 로그 중앙값 기준:

- 새 자연어 Task 입력: 10초 이하
- 아침 가용 시간·컨디션 확인: 30초 이하

중앙값과 함께 P90을 보고하여 일부 사용자에게만 극단적인 불편이 생기는 문제를 숨기지 않는다.

### 27.10 출시 판정

#### Pass

다음을 모두 만족해야 한다.

1. 모든 안전·권한·Planner Hard Gate 통과
2. Hard Deadline 추출 합격선 통과
3. 외부 실행 합격선 통과
4. Outcome Gate 10개 중 최소 8개 통과
5. 계획 시간 감소, 결정 부담 감소, Week 4 잔존율, 자동화 신뢰는 필수 통과
6. 시스템 원인 Hard Deadline 지연 0건

#### Conditional Pass

- 안전·권한·Planner Hard Gate는 전부 통과
- 필수 Outcome Gate는 전부 통과
- 비필수 Outcome Gate 최대 1개만 목표의 10% 이내 미달
- 수정 계획과 재평가 날짜가 확정됨

#### Fail

다음 중 하나면 실패다.

- 개인정보·권한 침해 1건
- 승인 없는 외부 행동 1건
- 실패를 성공으로 표시 1건
- 중복 Calendar Event 1건
- 슬롯 중복 또는 의존성 위반 1건
- 시스템이 직접 원인이 된 Hard Deadline 손해
- 필수 Outcome Gate 미달
- 자동화 신뢰 중앙값 4.5/7 미만

## 29. 주요 제품 위험과 대응

### 29.1 잘못된 자동 등록

**위험:** LLM이 마감이나 프로젝트를 잘못 해석한다.

**대응:** 원본 보존, 신뢰도, 중요도 기반 확인, 출처 충돌 탐지, 스키마 검증, 되돌리기.

### 29.2 계획의 과도한 변경

**위험:** 에이전트가 새 정보마다 계획을 바꿔 사용자를 혼란스럽게 한다.

**대응:** 계획 안정성 구간, 변경 비용, 기존 계획 최소 수정, 계획 변경 횟수 지표.

### 29.3 계획 엔진에 대한 과신

**위험:** 예상 시간이 틀리는데 시스템이 확정적인 계획처럼 표현한다.

**대응:** 기준·안전 예상 시간 분리, 불확실성, Unknown 위험 등급, 전역 Base·Safety Pass, 실제 기록 기반 보정.

### 29.4 자동화 불신

**위험:** 일정이 마음대로 바뀌어 사용자가 서비스를 떠난다.

**대응:** 단계적 권한, 승인 센터, 이유 보기, Audit Event와 되돌리기.

### 29.5 알림 피로

**위험:** 너무 많은 경고와 체크인이 발생한다.

**대응:** Critical·Actionable·Summary·Silent 분류, 중복 제거, 발송 전 유효성 재검사.

### 29.6 외부 연동 실패

**위험:** 내부 계획과 캘린더가 불일치한다.

**대응:** Outbox, 멱등성, 외부 ID, 내부·외부 상태 분리, 실패의 명시적 표시.

### 29.7 지나치게 큰 MVP

**위험:** 연동과 멀티에이전트 개발에 시간을 쓰고 핵심 계획 가치가 검증되지 않는다.

**대응:** Google Calendar 한 종류만 지원, 개인 중심, 모듈형 모놀리스, LLM Worker 최소화, 비목표 고정.

## 30. 구현 전 반드시 유지할 결정

다음 결정은 구현 편의를 이유로 변경하면 안 된다. 변경이 필요하면 별도 설계 변경 승인을 받아야 한다.

1. Planning Core가 단일 기준 데이터다.
2. LLM은 DB와 외부 도구를 직접 수정하지 않는다.
3. 계획 엔진은 LLM 없이 결정론적으로 실행된다.
4. Hard Deadline과 고정 일정은 사용자 승인 없이 변경되지 않는다.
5. 외부 실행은 멱등성과 실제 성공 검증을 가진다.
6. 인박스 원본과 구조화 결과를 함께 보존한다.
7. 실행 진행률과 마감 가능성을 분리한다.
8. 가용 시간을 100% 계획하지 않는다.
9. 과부하 시 추가 노동보다 범위·우선순위 협상을 먼저 한다.
10. 계획 재생성보다 최소 변경 재계획을 우선한다.
11. 내부 저장과 Google Calendar 반영 상태를 분리한다.
12. 사용자 데이터 소유권과 객체 버전을 모든 변경에서 검증한다.
13. 하나의 Planner Pass에서 시간 슬롯은 정확히 하나의 Task·일정·버퍼만 사용할 수 있다.
14. 마감 위험은 독립적인 작업 점수가 아니라 전역 Base·Safety Pass 배정 결과로 계산한다.
15. 출시 판정은 사전에 고정한 안전 Hard Gate와 정량 파일럿 합격선을 통과해야 한다.

## 31. 설계 완료 기준

이 설계는 다음을 모두 정의하므로 구현 계획을 작성할 수 있는 상태다.

- 문제와 대상 사용자
- 제품 목표와 비목표
- 개인 중심·팀 맥락 범위
- 사용자 일일·주간 운영 루프
- 자율성과 승인 정책
- Planning Core 정보 모델
- 작업 상태, 의존성, 완료 조건과 실제 시간
- 가용 시간, 우선순위, 위험과 과부하 계산
- 에이전트 역할과 공통 실행 루프
- 주요 화면과 알림 정책
- 기술 스택과 모듈 경계
- LLM 안전장치
- 비동기 처리와 외부 연동
- 오류·보안·감사 설계
- 테스트와 정량 품질 Gate
- 전역 슬롯 배정·동률 규칙·재계획의 규범 알고리즘
- 골든 데이터셋·4주 파일럿·출시 판정 프로토콜
- MVP 경계와 후속 확장

본 문서의 다음 단계는 **구현 계획 작성**이다. 구현 계획은 이 설계를 단계별 작업, 파일 범위, 테스트 우선순위, 마이그레이션과 검증 명령으로 변환해야 한다.

## 32. 용어 정리

- **Planning Core:** 프로젝트·작업·마감·계획의 공식 상태 저장소와 도메인 규칙
- **Area:** 학교, 프로젝트, 건강 같은 장기 생활 영역
- **Workstream:** 프로젝트, 과목, 공부 목표를 포괄하는 운영 단위
- **Milestone:** 제출, 발표, 시험과 프로토타입 같은 검증 가능한 결과
- **Task:** 지금 실행할 수 있는 행동 단위
- **Routine:** 반복 행동 템플릿
- **External Dependency:** 다른 사람이나 외부 조건의 결과를 기다리는 항목
- **Base Duration:** 현재 정보에서 가장 가능성이 높은 기준 예상 시간
- **Safety Duration:** 마감 안전성 계산에 사용하는 보수적 예상 시간
- **Base Pass:** 기준 예상 시간으로 생성하는 전역 실행 가능성 계획
- **Safety Pass:** 안전 예상 시간과 필수 버퍼로 생성하는 전역 마감 안전성 계획
- **Coverage Ratio:** 전역 배정에서 마감 전 실제로 확보한 시간과 필수 수요의 비율
- **Plan Snapshot:** 특정 시점의 계획 버전
- **Proposal:** 아직 실행되지 않은 변경안
- **Approval:** 특정 제안과 객체 버전에 대한 사용자 승인
- **Audit Event:** 변경 주체, 전후 값, 이유와 결과 기록
- **Focus Block:** 실행 시간이 확정되어 Google Calendar에 생성되는 집중 작업 일정
